gem-api.thirdbear.net — API NOTES + COMPOSE PAGE WISHLIST
===================================================================
2026-02-10 | EJ Fox + Claude | API v3.0.0

Hi! We've been migrating the gem-viz frontend off DuckDB onto the
REST API. It's going great — most pages are on the API now. Below
are a few things we noticed and a wishlist for the /compose page.

===================================================================
1. asset_type FILTER — NOT YET WIRED UP
===================================================================

The /assets endpoint accepts asset_type= but it doesn't seem to
be hooked up to the query yet. All values return the full 51188.

# TEST 1: no filter (baseline for comparison)
curl -s "https://gem-api.thirdbear.net/assets?limit=1" | jq '{total, first_type: .results[0].asset_type}'
# → {"total": 51188, "first_type": "Coal Mine"}
# This is the expected baseline — all 51188 assets.

# TEST 2: filter by slug "coal-plant"
curl -s "https://gem-api.thirdbear.net/assets?asset_type=coal-plant&limit=1" | jq '{total, first_type: .results[0].asset_type}'
# → {"total": 51188, "first_type": "Coal Mine"}
# Expected: ~14K coal plants only. Got full dataset instead.

# TEST 3: filter by exact DB value "Coal Plant"
curl -s "https://gem-api.thirdbear.net/assets?asset_type=Coal%20Plant&limit=1" | jq '{total, first_type: .results[0].asset_type}'
# → {"total": 51188, "first_type": "Coal Mine"}
# Same — total unchanged, first result is a Coal Mine not Coal Plant.

# TEST 4: a value that doesn't exist at all
curl -s "https://gem-api.thirdbear.net/assets?asset_type=DOESNOTEXIST&limit=1" | jq '{total, first_type: .results[0].asset_type}'
# → {"total": 51188, "first_type": "Coal Mine"}
# Expected: 0 results. Got 51188 — param appears to be accepted but not applied.

For reference, status and country filters work great:

# TEST 5: status=operating filters correctly
curl -s "https://gem-api.thirdbear.net/assets?status=operating&limit=1" | jq .total
# → 32989 ✓

# TEST 6: country=India filters correctly
curl -s "https://gem-api.thirdbear.net/assets?country=India&limit=1" | jq .total
# → 3436 ✓

# TEST 7: combining asset_type with status — only status applies
curl -s "https://gem-api.thirdbear.net/assets?asset_type=coal-plant&status=operating&limit=1" | jq '{total, first_type: .results[0].asset_type}'
# → {"total": 32989, "first_type": "Coal Mine"}
# 32989 matches status=operating alone — asset_type had no effect.

FYI — our tracker slugs map to these API type names:
  coal-plant   → Coal Plant              gas-plant  → Oil & Gas Plant
  coal-mine    → Coal Mine               iron-mine  → Iron Ore Mine
  steel-plant  → Iron & Steel Plant      bioenergy  → Bioenergy Plant
  gas-pipeline → Natural Gas Transmission Pipeline

We're currently working around this with client-side filtering
(ownership-api.ts listAssetsByType), but it's slow — fixing
asset_type would save a lot of unnecessary API calls.

===================================================================
2. MULTI-VALUE FILTERS — NOT YET SUPPORTED
===================================================================

Passing comma-separated values returns 0 results. Would be really
helpful to support OR-style multi-select (status=operating,planned).

# TEST 1: single value works fine
curl -s "https://gem-api.thirdbear.net/assets?status=retired&limit=1" | jq .total
# → 10878 ✓

# TEST 2: another single value also works
curl -s "https://gem-api.thirdbear.net/assets?status=operating&limit=1" | jq .total
# → 32989 ✓

# TEST 3: comma-separated — returns 0 instead of union
curl -s "https://gem-api.thirdbear.net/assets?status=retired,planned&limit=1" | jq .total
# → 0
# Expected: ~16995 (10878 retired + 6117 planned). Looks like the comma
# is being treated as part of the value rather than a separator.

# TEST 4: another combo — also 0
curl -s "https://gem-api.thirdbear.net/assets?status=operating,retired&limit=1" | jq .total
# → 0
# Expected: ~43867 (32989 + 10878).

===================================================================
3. COMPOSE PAGE (/compose) — MIGRATION WISHLIST
===================================================================

The compose page is an interactive faceted search/filter tool.
Currently runs 14 DuckDB queries against local parquet files.
Here's what we'd need from the API to migrate it fully.

Files: compose-queries.ts, compose-state.svelte.ts, filter-state.js

-------------------------------------------------------------------
3a. FIELDS WE'D LOVE ON /assets RESPONSES
-------------------------------------------------------------------

Currently returns:
  asset_id, asset_name, asset_type, operating_status,
  capacity_value, capacity_unit, country, state_province,
  latitude, longitude, url

Would be amazing to also have:
  owner_name           ← from ownership join
  owner_entity_id      ← from ownership join
  owner_hq_country     ← from entity join via owner
  ownership_share      ← percentage from ownership table
  start_year           ← from tracker source data

These 5 fields are in our DuckDB ownership table and make up
5 of the 11 columns in the compose page's results table.
This is the biggest blocker for migrating the page.

-------------------------------------------------------------------
3c. PRIORITIZED WISHLIST
-------------------------------------------------------------------

Would help a ton:
  1. Wire up asset_type filter on /assets
  2. Add owner_name, owner_entity_id, owner_hq_country,
     ownership_share, start_year to /assets response
  3. Multi-value filter support (status=operating,planned)
  4. sort= param (capacity_desc, name_asc, etc.)

Would let us fully replace DuckDB:
  5. POST /assets/search with faceted response:

     Request:
       { "asset_type": ["Coal Plant"],
         "status": ["operating", "planned"],
         "country": ["India"], "owner_name": ["TEPCO"],
         "capacity_min": 100, "q": "power",
         "sort": "capacity_desc", "limit": 50, "offset": 0 }

     Response:
       { "total": 1234,
         "results": [ ...assets w/ owner fields... ],
         "facets": {
           "asset_type": {"Coal Plant": 800, "Oil & Gas Plant": 434},
           "status":     {"operating": 900, "planned": 334},
           "country":    {"India": 600, "China": 400} },
         "stats": {
           "capacity_range": {"min": 0.5, "max": 4800},
           "start_year_range": {"min": 1960, "max": 2028} } }

     Facets use parametric counting (each excludes its own filter).
     This one endpoint would replace all 14 of our DuckDB queries.

Nice to have:
  6. POST /assets/export — streaming CSV/JSON, no 500 limit
     (for "Export all" and "Select all matching" features)

With item 5: compose page fully off DuckDB. One API call
  replaces everything.

With item 6: bulk export and select-all features work.

Thanks for all the work on the API — it's been great to use
